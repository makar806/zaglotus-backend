# Заглотус Backend

Серверная часть тамагочи, который питается закрытыми дедлайнами. Пользователь создаёт питомца и дедлайны. После закрытия дедлайна питомец получает одну еду и опыт: `EASY` — 20, `MEDIUM` — 50, `HARD` — 100. Каждые 100 очков опыта повышают уровень.

## Что реализовано

- регистрация и вход по JWT;
- безопасное хранение паролей с BCrypt;
- питомец создаётся вместе с пользователем;
- создание, просмотр, изменение и удаление открытых дедлайнов;
- фильтрация дедлайнов по статусу;
- закрытие дедлайна с начислением еды и опыта;
- запрет повторного закрытия и изменения закрытого дедлайна;
- PostgreSQL и автоматические миграции Flyway;
- транзакции регистрации и кормления питомца;
- блокировки строк при кормлении для защиты от параллельных запросов;
- валидация запросов, понятные ошибки и корректные HTTP-статусы;
- логирование запросов и ошибок;
- unit-тесты основной бизнес-логики;
- воспроизводимый запуск через Docker Compose.

## Запуск

Нужен Docker с поддержкой команды `docker compose`.

```bash
cp .env.example .env
docker compose up --build
```

Сервер будет доступен на `http://localhost:8080`. Миграции применяются автоматически при старте приложения. Проверка состояния:

```bash
curl http://localhost:8080/health
```

Интерактивная документация Swagger UI:

```text
http://localhost:8080/swagger
```

Исходная OpenAPI 3.0.3 спецификация:

```text
http://localhost:8080/openapi.yaml
```

В Swagger сначала выполните `POST /api/v1/auth/register` или `POST /api/v1/auth/login`. Скопируйте `token` из ответа, нажмите кнопку `Authorize` и вставьте токен без префикса `Bearer`. После этого можно отправлять защищённые запросы прямо из браузера.

Остановка:

```bash
docker compose down
```

Удалить также локальные данные PostgreSQL:

```bash
docker compose down -v
```

## Быстрая проверка API

Регистрация:

```bash
curl -X POST http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"name":"Иван","email":"student@example.com","password":"password123","petName":"Жора"}'
```

Из ответа нужно скопировать поле `token`. Дальше вместо `TOKEN` подставляется его значение.

Создание дедлайна:

```bash
curl -X POST http://localhost:8080/api/v1/deadlines \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer TOKEN' \
  -d '{"title":"Сдать лабораторную","description":"Подготовить сервер","dueAt":"2027-10-22T18:00:00Z","difficulty":"HARD"}'
```

Получение списка:

```bash
curl http://localhost:8080/api/v1/deadlines?status=OPEN \
  -H 'Authorization: Bearer TOKEN'
```

Закрытие дедлайна:

```bash
curl -X POST http://localhost:8080/api/v1/deadlines/DEADLINE_ID/complete \
  -H 'Authorization: Bearer TOKEN'
```

Состояние питомца:

```bash
curl http://localhost:8080/api/v1/pet \
  -H 'Authorization: Bearer TOKEN'
```

## Архитектура

Приложение является модульным монолитом и разделено на три понятных слоя:

- `domain` — сущности `User`, `Pet`, `Deadline`, бизнес-правила, исключения и интерфейсы репозиториев;
- `application` — сервисы сценариев, JDBC-реализации репозиториев, транзакции, безопасность и конфигурация;
- `presentation` — Ktor-контроллеры, DTO запросов и ответов, обработка HTTP-ошибок и запуск приложения.

Сущности сами защищают свои правила. Например, `Deadline` запрещает повторное закрытие и изменение после закрытия, а `Pet` начисляет опыт, еду и уровень. Application-сервисы только организуют последовательность действий.

Сервисы зависят от интерфейсов `UserRepository`, `PetRepository` и `DeadlineRepository` из domain, а не от JDBC. Реализации этих интерфейсов лежат в `application/persistence`. Поэтому PostgreSQL можно заменить другим хранилищем без изменения сущностей, сервисов и контроллеров. Ktor также находится только в presentation, поэтому вместо REST можно добавить другой API-слой.

Ktor принимает HTTP-запросы. HikariCP управляет пулом соединений. Flyway последовательно применяет SQL-миграции. JDBC используется напрямую, чтобы работа транзакций и SQL была видна без дополнительной ORM. kotlinx.serialization преобразует JSON. BCrypt хеширует пароли, а JWT используется для авторизации.

## Транзакции и конкурентность

Пользователь и питомец создаются в одной транзакции. Закрытие дедлайна и изменение питомца также выполняются одной транзакцией через интерфейс `TransactionManager`. Application-сервис не зависит от JDBC-транзакции напрямую. Перед изменением строки дедлайна и питомца блокируются через `SELECT ... FOR UPDATE`. Если одновременно придут два запроса на закрытие, второй увидит уже закрытый дедлайн и получит `409 Conflict` без повторной награды.

## Конфигурация

Приложение читает настройки из переменных окружения:

| Переменная | Назначение |
|---|---|
| `DB_URL` | JDBC URL PostgreSQL |
| `DB_USER` | пользователь БД |
| `DB_PASSWORD` | пароль БД |
| `JWT_SECRET` | секрет подписи токенов |
| `JWT_ISSUER` | издатель токена, по умолчанию `zaglotus` |
| `JWT_AUDIENCE` | аудитория, по умолчанию `zaglotus-users` |
| `JWT_REALM` | realm, по умолчанию `zaglotus-api` |
| `PORT` | порт, по умолчанию `8080` |

Файл `.env` не попадает в Git. Значения из `.env.example` подходят только для локальной разработки.

## Тесты

Для запуска нужен JDK 21. Устанавливать Gradle отдельно не требуется:

```bash
./gradlew test
```

Тесты проверяют domain-правила и application-сервисы: регистрацию, нормализацию email, создание питомца, запрет дубликатов, проверку пароля, валидацию дедлайнов, награды, уровни, фильтрацию и защиту от повторного закрытия.
